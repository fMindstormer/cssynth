cssynth · write-up

Compiling pictures to CSS

CSSBattle shows you a flat picture and asks for the shortest HTML and CSS that draws it. cssynth is a compiler that plays it: give it the picture, and it searches for the code. Here is how it works, what each idea is worth, and where it still loses to people.

The game, and why it is a compiler problem

CSSBattle targets are 400×300 pictures with a handful of flat colors: boxes, circles, rounded bars, the odd triangle. You write HTML and CSS that renders the same picture, and the shortest code at a full match wins. Players golf hard: no doctype (so the page renders in quirks mode and padding:50 needs no unit), unclosed tags, colors in their shortest spelling.

It looks like image fitting, but two things make it a compiler problem. The cost is characters, not shapes: a circle is cheap, a five-point clip-path:polygon(…) costs 40–60 characters, and a shape that repeats can be a box-shadow of another for 10–20. And the renderer is fixed: Chromium decides where every edge falls and how it is smoothed, so a plan that is right in an idealized model can be wrong by a band of pixels along every edge.

One number

Everything in cssynth is scored by a single objective:

J = characters + wrong pixels / ρ

A pixel is wrong if any channel is more than 8/255 off. ρ is how many wrong pixels the compiler accepts to save one character. The default is 0.5, so two wrong pixels cost as much as a character and it almost never gives up accuracy for length. Search variants, clean-up moves and re-search steps are all accepted or rejected by J, and the character count comes from running the real code generator, not from an estimate.

A greedy search that can paint underneath

The core loop adds one shape at a time. Candidates come from the error: for every connected region of still-wrong pixels of one color, it proposes the region's box, its ellipse, boxes with various rounded corners, a 45° diamond, a bar and a leaf along the region's main axis, and polygons from the region's convex hull and from its traced outline. The most promising are hill-climbed on their edges, corner radii, rotation or vertices, and the best one goes in.

The detail that matters most: a new shape can go at any depth in the stack. For each depth, its value is computed against the canvas below that depth, counting only the pixels the shapes above leave visible. That is how rings, eyes and nested figures get built: the hole is found first, and the disc slides in underneath it.

Switching insertion at any depth off, so that new shapes always go on top, raises the total J over the benchmark by {{abl:top-only}}, one of the three largest effects of any single part.

Putting length into the search

A plain greedy search picks the shape that fixes the most pixels. That ignores what it costs to write: a polygon and a rounded box that fix about as many pixels look the same, though one is twice as long. So the search has a second mode, which picks the shape with the best

pixels fixed / ρ − estimated characters

The estimate is the shape's own element, or one box-shadow entry when the shape is a shifted copy of one already placed. Repeats get cheaper as the search goes, so it learns to prefer the copy. Neither mode is always better (a cheap shape now can leave more to draw later), so every search runs both ways and J picks the winner. On the benchmark the length-aware mode wins on {{length_wins}} of {{n}} targets. Running both cut {{length_chars}} characters in total, and twice the searches take about as long as before, because the length-aware ones stop with fewer shapes.

Box-shadows as a constraint problem

Box-shadows are the golfer's copy-paste: box-shadow:35px 0 #fff,70px 0 #fff repeats a box for a few characters per copy. But a shadow is painted just below its own element, so grouping shapes as shadows of one another changes the paint order, and shapes that overlap with different colors have to keep their order.

cssynth solves the grouping and the paint order together with CP-SAT. Each shape is either an element or a shadow of one compatible element. Each gets a paint position, which a shadow shares with its anchor. For every pair that must stay in order, the positions strictly increase unless both are in the same group, which rules out cycles. The objective is the characters of the elements, the shadow entries and the box-shadow: declarations.

Keeping the model honest

The search scores shapes with its own rasterizer, because it evaluates hundreds of thousands of them. A gain is a few lookups in running sums along pixel rows, over the runs of pixels each shape covers, cached by shape and checked to give bit-identical answers to the full rasterizer. But the benchmark scores what Chromium actually draws: every output is rendered in headless Chromium and compared with the target, pixel by pixel. Where the two disagreed, the model was fixed rather than tuned around:

  • Chromium rounds a rotated box's position to whole pixels before rotating it.
  • A spread larger than a corner radius bends the shadow's corner, so those shapes never become shadows.
  • Chromium evaluates gradients at pixel centers and does not smooth hard stops. Targets drawn with rotated boxes have smoothed edges, so a hard-stop gradient leaves a band of wrong pixels along each one. cssynth fits each boundary to a sub-pixel position with a short linear ramp, which Chromium draws within 3/255 of the model.

Where it still loses

The greedy search commits to the shape that looks best now. A re-search pass takes the best result apart (one polygon at a time, then one color at a time), refills the gap and keeps whatever lowers J, which repairs some of those choices, but not the structural ones.

Hill climbing makes this hard to fix locally: start from one circle, and the climb grows it back into the tall box, because that fixes more pixels. What would find the human plan is a search that compares whole programs: two circles plus a cheap shadow against one box plus patches. That is the next step, along with gradients on shapes, borders and repeating a shape with ::before/::after.

Try it

The compiler is pure Python (NumPy and SciPy, with OR-Tools for the shadow grouping when it is installed), so it also runs in the browser. The demo loads it with Pyodide and compiles your picture locally. The source, the benchmark and a longer write-up of the method are on GitHub.
